1. What is SupplyGuard?

SupplyGuard is an educational software-delivery and software-supply-chain demonstration. It helps a beginner see how code can move through checks and into a deployment, and how teams can respond when a check or service fails.

  • Browser simulator: A dashboard with mock CI/CD pipelines, environments, security findings, logs, monitoring, and a digital supply network.
  • Scanner API: A Python web service that accepts text files, looks for a small set of common risks, and saves scan summaries for signed-in users.
  • Operations examples: Docker Compose, Prometheus/Grafana configuration, Kubernetes manifests, Terraform for AWS, and GitHub Actions workflows.
Best way to think about it: the simulator is a training model; the scanner API is the part that actually processes submitted files. The displayed simulated cloud is not connected to a real cloud account.

3. The browser workflow

When a browser requests the site root, FastAPI returns frontend/index.html. The page loads its stylesheet and JavaScript. The JavaScript builds the navigation and page content in the browser.

  1. Start: The app creates a simulation object and draws the Overview page.
  2. Choose a page: Navigation selects Overview, CI/CD Simulator, Supply Network Simulator, DevOps Environments, Supply Chain Security, Deployments, Monitoring, Logs, Cloud Architecture, Settings, or Project Scanner.
  3. Take an action: Buttons select scenarios, run or pause a pipeline, simulate an incident, adjust stock, or view reports.
  4. Update the display: Browser-side JavaScript changes the in-memory demo state, re-renders the selected page, and shows a toast message.
  5. Refresh sample events: The supply-network simulation advances on a timer. Some preferences, such as simulation speed, are saved in browser local storage.

Pipeline stages in the simulator

Source → Build → Unit tests → Code quality → Security scan → Package → Deploy. A successful scenario moves through each stage. Failure scenarios stop at a selected stage, mark later stages as skipped, and display a sample cause, impact, and recommended response.

  • Build failure: a mock missing-lockfile problem.
  • Test failure: a mock regression stops release progress.
  • Security vulnerability / supply-chain attack: a mock security gate blocks a suspicious release.
  • Deployment rollback / infrastructure incident: a mock health or infrastructure issue halts or rolls back release progress.

4. Supply network and security demonstrations

Digital supply network

The network page uses sample inventory items, supplier scorecards, and shipments. A periodic browser timer advances sample delivery events. Buttons can simulate a stock shortage, delay a shipment, disrupt a supplier, receive replenishment, pause updates, or restore the sample data.

For example, “available stock” is calculated as on hand − reserved. It is compared with the sample reorder point to label an item healthy, low-stock, or needing a reorder. Those numbers are demonstration values stored in JavaScript, not a connection to a warehouse system.

Security and operations pages

  • Supply Chain Security: displays sample vulnerabilities, SBOM rows, artifact trust information, and example policy gates.
  • Deployments and environments: show mock release history and development/test/staging/production health.
  • Monitoring and logs: display simulated health signals and pipeline events.
  • Cloud Architecture: draws an educational source-to-deployment flow and explicitly marks services as mocked.
Learning point: a dashboard can be realistic-looking while still being a simulator. Before acting on a finding, confirm whether the data came from a real scan, an external data source, or sample code.

5. How the scanner API works

The backend is a FastAPI application in Python. The web server serves the home page and static files and also exposes API routes. The OpenAPI documentation is available at /docs while the server is running.

→
2. Send filesPaths + text contents
→
3. ValidateCheck request limits and paths
→
4. Scan + policyFind and filter risks
→
5. Save reportSQLite scan summary

The API processes submitted file text in memory. It does not open arbitrary local paths on the server.

EndpointPurpose
GET /api/healthSimple service-health response.
POST /api/auth/registerCreate an account and return an access token.
POST /api/auth/loginCheck credentials and return a token.
GET /api/auth/meReturn the signed-in account when a valid bearer token is supplied.
GET /api/policiesList enabled scanning policies for the signed-in user.
POST /api/scansScan supplied files and save the report.
GET /api/scans, GET /api/scans/{id}Read scan history belonging to the signed-in user.
GET /metricsExpose a few static demo metrics in Prometheus format.

What the scanner checks

  • Credential-like strings in source text (pattern matching, not a complete secret scanner).
  • Python requirements entries without an explicit version.
  • JavaScript dependencies set to */latest, or using floating ^/~ ranges.
  • A recognized dependency manifest without a recognized lock file.
  • Dockerfiles without a USER instruction or with an unpinned base image.
  • Invalid JSON in package.json.

Findings have a rule ID, severity, file path, optional line, explanation, and recommendation. The policy engine keeps only findings whose policy is enabled. A risk score is calculated from severity weights and capped at 100. The scan is marked blocked for a critical finding, attention when findings remain, and passed when there are none.

Limits: The API accepts up to 500 files and 5 MB of total UTF-8 text per scan. These lightweight static rules do not query a live vulnerability database and cannot prove that dependencies are safe.

6. Accounts, data, and safety

  • Passwords: The backend stores a password hash rather than the original password.
  • API sessions: The backend signs expiring bearer tokens using SECRET_KEY.
  • Access control: Scan history queries are scoped to the authenticated user.
  • SQLite: The database stores accounts, policies, scan metadata, and serialized findings. The scanner comments that uploaded file contents are not stored in the scan history.
  • Input checks: Pydantic models validate request fields; scanner paths reject absolute paths and paths containing parent-directory traversal.
  • Local storage: The simulator keeps some client-side state/settings in the browser; this is separate from API account and scan records.
Before real use: create a private, strong random SECRET_KEY in .env, keep that file private, restrict CORS origins for a deployment, and do not upload sensitive files unless you trust the server. Never treat demo security scores as production audit results.

Policy files

The API policy catalog is seeded in database/seed.sql. The separate Rego example in policies/supply_chain.rego demonstrates a policy-as-code decision: critical findings block and high findings trigger attention. It is an example policy file, not evidence that the Rego engine is called by every API scan.

7. Run the project with Docker

Docker Compose can start the application and its local monitoring tools. Run these commands from the project directory in PowerShell. Docker Desktop must be installed and running.

cd D:\KARUNYA\Projects\supplyguard
Copy-Item .env.example .env
# Edit .env and replace SECRET_KEY with a long random value.
docker compose up --build

Then open:

  • http://localhost:5050 — SupplyGuard web page.
  • http://localhost:5050/docs — interactive API documentation.
  • http://localhost:5050/api/health — app health response.
  • http://localhost:9090 — Prometheus, if its Compose service starts.
  • http://localhost:3000 — Grafana, if its Compose service starts. The current Compose file has a demo admin password setting; change it before exposing Grafana beyond a trusted local machine.

Compose keeps the SQLite database and monitoring data in named Docker volumes. Stop foreground services with Ctrl+C; to stop and remove the Compose containers, run docker compose down. Named volumes are separate and remain unless explicitly removed.

Ports: The app uses port 5050 by default. Compose allows the application port to be changed with PORT; Prometheus and Grafana use PROMETHEUS_PORT and GRAFANA_PORT. Ensure those host ports are free.

Local Python alternative

cd D:\KARUNYA\Projects\supplyguard
python -m venv .venv
.\.venv\Scripts\Activate.ps1

pip install -r requirements.txt

When using the local Python option, open the same page at http://127.0.0.1:5050. To check the running container, use docker compose ps and docker compose logs -f supplyguard.

8. Monitoring, tests, and deployment examples

Local observability

The application exposes /metrics. Prometheus is configured to scrape the app, and Grafana has a preconfigured data source and dashboard. The metrics currently describe demo state (such as a simulator-mode flag and fixed sample counts); they are not measurements of actual cloud workloads.

Automated checks

The GitHub Actions CI workflow installs Python/Node/Terraform tools, runs pytest, checks JavaScript syntax, validates Terraform formatting and configuration, checks Docker Compose, and builds the application image.

Deployment examples

  • Kubernetes: namespace, deployment, service, ingress, persistent storage, health probes, and non-root container settings are provided as example manifests. Replace example names/images and supply a real secret before using them.
  • AWS with Terraform: describes a VPC, load balancer, ECS Fargate service, ECR image repository, EFS persistence, and CloudWatch logs.
  • GitHub deployment workflow: demonstrates publishing an image to ECR and applying Terraform with AWS credentials through GitHub OIDC.
These are deployment templates, not a live deployment. They need cloud accounts, permissions, secrets, correct image names, and careful review. AWS resources may incur cost. The Kubernetes image name and sample secret must be replaced before deployment.

10. Beginner glossary and exercises

API

A defined way for one program to ask another program for data or work.

CI/CD

Continuous integration and delivery: automate checks and release steps after code changes.

Dependency

External software that a project uses.

Lock file

A file that records exact dependency versions so installs are more repeatable.

SBOM

Software bill of materials: a list of components in a software product.

Container

A packaged app and its runtime pieces, designed to run consistently in different environments.

Bearer token

A temporary credential sent with an API request to show that a user is signed in.

Prometheus / Grafana

Tools commonly used to collect metrics and show them on dashboards.

Try these learning activities

  1. Run the “Test failure” pipeline scenario. Find the failed stage, the root cause, and the proposed next step.
  2. Run the “Supply-chain attack” scenario. Explain why a policy gate should stop an untrusted package.
  3. Simulate a stock shortage and explain how available inventory differs from on-hand inventory.
  4. Open /docs, register a test account, and inspect how the API describes a request and response.
  5. Submit a small test manifest to the scanner. Compare its findings with the rules in backend/scanner_engine.py.
  6. Change a sample policy in a local learning copy, then run the automated tests and explain the behavior change.

Educational note: SupplyGuard is a learning aid. Its mock dashboards and small static scanner are not substitutes for production monitoring, security review, vulnerability intelligence, or a complete supply-chain assurance program.
